# Claude AI Development Journal

A running log of the real process. Entries marked **Challenge** are places where the first output was wrong or
weak and was corrected.

## 1. Initial analysis
- Asked Claude to `/init`; the repo held only the brief (.docx) and a video. Claude read the brief by unzipping the docx
  and said plainly it could not watch the video. The repo-guidelines document was supplied afterwards and shaped the
  layout (README, docs/, prompts/, ai-journal/, Flyway, OpenAPI, one-command Docker).
- Stack choice (Java/Spring Boot, then Gradle) was mine; Claude recorded it.

## 2. Architecture
- Asked for microservices if allowed, otherwise a single app with Kafka inside. The brief explicitly asks what drives
  a service split, so Claude proposed **two services by read/write profile** (claims write side, reporting read side)
  plus a shared event-contract module.
- Accepted: outbox pattern, event-carried state with claim `version` for idempotency, claimId as the Kafka key.
- Accepted with assumptions documented: six markets guessed as SG/HK/MY/TH/ID/AU, no auth (header-based officer id),
  no FX.

## 3. Implementation
- Gradle wrapper: no Gradle on the machine, so Claude downloaded a distribution to a scratch dir to generate the wrapper.
- **Challenge:** a large single shell heredoc failed to parse and wrote nothing; Claude switched to writing files
  individually and verified nothing partial had been created.
- **Challenge (caught in review before first compile):** `Claim.version` was a primitive `long`. With an
  application-assigned UUID id, Spring Data would treat a new claim as existing and merge. Changed to `Long`.
- **Challenge:** first draft of `provideInfo` had a half-written condition and a stub method (`openRequestsAfter`
  returning false). Simplified to: flush the answer, then return the claim to review only when no open requests remain.
- **Challenge:** an unused import of `jakarta.persistence.AccessType` (does not exist in JPA 3.1) would have broken the build; removed.
- Test helper named `post` shadowed the statically imported MockMvc `post`; renamed to `act`.
- Schema SQL initially used `AUTO_INCREMENT` (H2 only); changed to `GENERATED BY DEFAULT AS IDENTITY`, valid on
  both H2 and PostgreSQL.

## 4. Testing
- 19 tests: lifecycle unit tests, full API flow on real Flyway schema, outbox event ordering/versions, validation and
  error codes, projection idempotency/staleness, exposure/workload/performance reports.
- Both services also run standalone (jars) and `/actuator/health` was UP; OpenAPI specs were exported from the running
  services.

## 5. Verification gaps (stated honestly)
- Docker daemon was not running on this machine: `docker compose config` validates, but `docker compose up --build`
  and live Kafka end-to-end were **not** exercised. No automated test covers the Kafka transport itself.
  To do before submission: run `docker compose up --build` and the README "Trying It" flow.

## 6. Final review
